Supply Chain P&L Dashboard

Most supply chain and finance teams already have the transactional data needed to see true cost-to-serve - it just isn't in a shape anyone can report from. I designed and built the full path from raw operational data to a decision-ready dashboard: a SQL-based ETL pipeline that turns transactional records into an analytics-ready model, feeding a dashboard that reports EBITAI margin down to the individual sales order for a €3.8B EU dairy network - refreshed automatically instead of rebuilt by hand in Excel every month.

The Business Problem

Facility, product, and customer profitability data usually exists — just scattered across transactional systems that were never designed to be queried directly for reporting. So it gets pulled by hand: exported from the ERP, allocated in Excel, rebuilt every reporting cycle. That makes it slow, inconsistent between analysts, and rarely granular enough to catch a problem at the individual order level.

This project replaces that manual cycle with an automated pipeline: raw operational tables - sales orders, internal transfers, and inventory - flow through a SQL transformation layer into one analytics-ready model, and that model feeds a dashboard built for three different audiences: executives get headline trends, network planners get facility-level cost breakdowns, and commercial teams get customer- and channel-level margin views.

From Raw Transactions to an Analytics-Ready Model

The source data starts life as OLTP - the operational tables an ERP writes to every time an order is placed, a shipment moves, or inventory updates.

Why not build the dashboard straight off the operational tables?

  • It's built for writes, not aggregation. OLTP schemas are normalized into many narrow tables to keep transactions fast and consistent - exactly the structure that makes cross-table analytical queries (margin by customer, by channel, by month) slow and expensive to run.
  • It only knows "now." Operational tables typically hold current state, not history - there's no clean way to see a trend over time unless that history is captured somewhere else, on a schedule.
  • It isn't one story yet. Facility, customer, product, and cost data live in separate tables with separate keys - analyst still has to define how they join and what the resulting numbers mean before a dashboard can use them.

The fix is a separate OLAP layer: a model built specifically for reporting, refreshed on a schedule, decoupled from the live transactional system, and shaped so a dashboard tool can query it directly and cheaply. Getting there is the ETL pipeline's job.

The whole pipeline is written in SQL and orchestrated with dbt, so every transformation is version-controlled, testable, and documented - not a one-off script. Staging does no logic at all; intermediate models are where the cost allocation actually happens (that logic is the analytical core of the project, so I'm keeping it out of this write-up for now); the mart is what Looker Studio reads from. What matters for the dashboard layer is simply what comes out the other end - one row per sales order, carrying:

Sales Value COGS Transport Cost Handling Cost Storage + Overhead SG&A Facility · Product · Customer · Channel keys

From those, the mart derives the profitability waterfall the dashboard reports on:

GM     = Sales Value - COGS
Profit    = GM - (Transport + Handling + Storage + Overhead)
SG&A   = 3.5% × Sales Value
EBIT = Profit − SG&A

Designing the Dashboard

Having a clean, analytics-ready mart is only half the job - the other half is deciding what each audience actually needs to see, and in what form. For each of the three views, I started from the decision the audience is making, then worked backward to the KPIs and chart types that support it.

Executive Summary

Decision: is overall profitability healthy, and is it moving in the right direction?

  • Headline KPIs: Sales Value, EBIT, EBIT Margin, Volume
  • Trend line for EBIT over time - surfaces direction, not just a snapshot
  • Margin by product category - flags where to look next

Network & Facility Performance

Decision: where in the network is cost-to-serve out of line?

  • Per-facility sales and EBIT margin, side by side
  • Cost breakdown by type (handling / storage / transport) - shows why a facility underperforms, not just that it does
  • Geographic view of sales value by customer, for network planning context

Customer & Channel Profitability

Decision: which accounts or channels are worth the volume they demand?

  • Account-level EBIT margin ranking
  • EBIT by channel
  • Sales-value-vs-margin scatter - deliberately chosen to flag high-volume, low-margin accounts in one view rather than two separate tables

The common thread across all three: every chart maps to a specific question someone in that role would actually ask, and every number on screen traces back to a single, tested definition in the mart - so a finance controller and a network planner are always looking at the same underlying truth, just sliced differently for their decision.
