AI Network Design Assitant

A prototype that compresses a 3-5 day supply chain network design process into a live conversation: describe a scenario in plain language, and an AI chatbot translates it into a structured adjustment that can be the input for supply chain optimization model - all inside one Streamlit dashboard, built in a single night with Claude Code.

View Github Repo

Context

On September 2nd, I joined the Claude Community Night in Nuremberg, where builders got Claude Code credits and one night to build a product from their own idea.

I brought an idea I'd been wanting to test, based on my previous work in supply chain consulting: an AI chatbot to support data adjustment in Network Design projects. In this type of project, we build a replication model of the physical supply chain network, so a manager can test new configurations - closing some warehouses, opening new ones, or rerouting flows - and see the impact on the operation's KPIs (cost, time-to-serve, and service level) before actually making the decision and implementing it.

Process Adjustment

The old workflow starts with receiving the request from the client. Based on that request and our technical understanding of the model, we - the consultants - create a list of adjustments we need to make to the data and model. We then apply those adjustments to prepare the data input, run the model, and load the output into an interactive dashboard built with a Python package called Streamlit, where we can compare scenario results, or go back and adjust the data input if we find something looks unexpected.

The whole process before usually takes three to five days end-to-end and involves at least two analysts. Here's what the new process design looks like:

Before: manual translation across three separate tools. Now: the AI chatbot handles translation inside the same Streamlit dashboard.

So instead of manually translating the client's request into a list of tasks and adjustments, we let the AI chatbot handle that step. And because everything is now integrated inside the same Streamlit dashboard, we can trigger the whole flow from beginning to end with much less human involvement.

Chatbot Implementation Design

To make sure the AI chatbot's translation (I use Claude Sonnet-5 as the LLM behind it, so I'll say "Claude" instead of "AI" from here on) is correct, there are four main design questions this setup needs to answer.

3.1 What can the user actually change?

To keep things manageable for the build night, I limited the chatbot to three scenario types the user can interact with:

  • What happens to the network if we close a specific warehouse?
  • What happens if we open a new warehouse?
  • What happens if we reroute an area to a different warehouse - like not letting the Nuremberg warehouse serve Thuringia's stores anymore?

In a real project, the number of scenario types would vary depending on the business requirement. So the first task is always defining the requirements, before writing any code.

3.2 What does Claude need to know to create data input correctly?

This step is actually really important, because it takes business and modelling knowledge to guide the chatbot so its output is correct. To do that, I define a tool for each case. Here's the close-warehouse case as an example (you can find the code in chat_assistant.py file): 

UPDATE_SCENARIO_TOOL = {
    "name": "update_scenario",
    "description": (
        "Apply a partial update to the network scenario — which warehouses are open "
        "or closed. Only include warehouses whose status should actually change; omit "
        "warehouses that stay as they are."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "wh_status": {
                "type": "object",
                "description": "Mapping of warehouse_id (e.g. 'WH001') -> 'open' or 'closed'.",
                "additionalProperties": {"type": "string", "enum": ["open", "closed"]},
            },
        },
        "required": ["wh_status"],
    },
}
  • "name": "update_scenario" - the identifier, so Claude knows which tool it's calling.
  • "description" - this is not just documentation for humans, it's part of the prompt Claude actually reads to decide when to use this tool and how. That's why it's written carefully: "only include warehouses whose status should actually change" is a direct instruction to Claude, preventing it from lazily dumping every warehouse's status into every call.
  • "input_schema" - this is a JSON schema, a standard format for describing what valid data looks like. Here it must be an object called wh_status, where each key is a warehouse ID and each value is the string "open" or "closed".

At runtime, this definition gets sent to the API alongside the user's message (tools=… in interpret_message()). If Claude decides "the user wants to close WH004," it returns a tool_use block like this: 

{"type": "tool_use", "name": "update_scenario", "input": {"wh_status": {"WH004": "closed"}}}

3.3 What should the LLM NOT have to deal with?

For a scenario where stores served by Warehouse A should now be served by Warehouse B, I don't ask Claude to list every store ID in its response - that's a waste of tokens, and it increases the chance Claude gets an ID wrong. Instead, Claude only needs to know which warehouse served the stores before, and which warehouse should serve them now.

So Claude translates "move Berlin's stores to Hamburg" into just berlin_id and hamburg_id, and a function, _stores_for_warehouse(), maps that adjustment onto the actual list of stores that need their routing changed.

This setup follows one principle: whenever a tool's parameters require something your database already knows, don't ask the LLM - resolve it in code after the tool call.

3.4 What if the LLM's response is subtly wrong or malicious?

In the case of updating a warehouse's status, even with the schema already in place, it doesn't fully guarantee correctness - it only guarantees the shape of the output. Claude can still hallucinate a value like {"WH999": "open"} for an ID that doesn't actually exist. So every response needs a check after it comes back: 

wh_status_patch.update({wh: status for wh, status in raw_status.items()
                        if wh in valid_wh_ids and status in ("open", "closed")})

Lesson Learned

So, after doing the first project ever that include AI Chatbot inside the process, here is some main lessons that I learned:

  • Start with the high-level picture first: decide which step in the process actually benefits from AI, because not every step needs it. Some steps - like preparing data input and running the model - only need to be automated with Python code.
  • Business understanding is very important, because it's what lets you guide the AI on what it should do in each case (through the tool definitions in this project).
  • Never trust AI 100%. You still need code to validate its output - like not letting Claude introduce a new warehouse ID when it should only be updating an existing one's status - and to check if the data adjustment was actually applied correctly.
  • Stay open to extending the AI's usage and scalability. Right now there are only three scenario types, but there's a lot more to explore - like consolidating import flows into certain warehouses before doing an internal transfer to the other warehouses, to save on import cost.
