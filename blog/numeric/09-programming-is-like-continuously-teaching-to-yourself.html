09. Programming is like, continuously teaching to yourself

Programming is actually a process of self-learning. Because technology changes incredibly fast, what schools provide is merely a foundation for us to take our own next steps.

Ngan Ho · December 15, 2024 · 5 min read

I recently took a course on the basics of programming covering Object-Oriented Programming. At the end of the course, right before the final exam, our instructor gave us an encouraging piece of advice:

“Programming is always like teaching to yourself. So I bring you the basic concept to empower you to learn and develop more.”

This means that programming is ultimately a continuous process of self-education. Because technologies in the industry shift rapidly, schools only equip us with foundational knowledge that can be adapted to any language or stack. From there, implementing and updating our technical skills is something we must learn on our own. I found this quote so inspiring that I used it as the title of this post—even though our primary focus today will be comparing two common programming paradigms: Object-Oriented and Procedural programming.

What are these two paradigms and how do they differ?

Object-Oriented Programming (OOP):

  • Your code structure, such as its internal methods, is built entirely around "objects".
  • If I define an object as a data table, then the computation logic I want to run on that table will be built specifically into it.
  • A completely separate object, like a standalone number, won't be able to utilize that data table's specific functions unless an explicit relationship is defined between them.
  • Common Object-Oriented languages include: C++, Java, Python, etc.

Procedural Programming:

  • The program layout is structured sequentially around functions or procedures.
  • For example, if I want to add up all input values together, I would build a generic sum() function.
  • Unless I set up custom constraints, all objects and variables can globally share and call this sum() function.
  • Common Procedural or functional-leaning languages include: C, Pascal, R, etc.

What are the pros and cons of each?

Object-Oriented Programming

Before jumping into the core benefits of OOP, let's introduce a special capability of objects: inheritance.

For instance, let's say I have a base object called "Student". The basic behaviors of a student might include:

  • Going to school
  • Listening to lectures
  • Doing homework

Now, I want to create a second object called "Class Monitor". A Class Monitor needs all the standard behaviors of a regular student, but possesses a unique extra responsibility: Managing the class.

In an OOP environment, to execute this design seamlessly, I would:

  1. Create the Student class.
  2. Define the standard methods within the Student class.
  3. Create the Class Monitor class as a subclass of Student, allowing it to automatically "inherit" all methods from Student.
  4. Add the specific "Managing class" method uniquely to the Class Monitor class.

From this example, you can see that the distinct advantage of OOP is reusability. Instead of rewriting all the shared student functions inside Class Monitor, we can simply leverage inheritance. In a massive, complex software system, this approach yields huge benefits by eliminating duplicate code blocks across different but related entities.

So, what's the drawback? Because entities in an OOP codebase are deeply interconnected, figuring out exactly what functions an object possesses requires tracing back through the code of all its parent objects. And if you weren't the one who originally wrote those classes? We all know how painful reading someone else's structural code can be haha :))

Procedural Programming

In contrast to OOP, if we look at the same scenario from a procedural perspective, I would simply write a standalone function called go_to_school() If I want both the Student and the Class Monitor to be at school, I apply that function directly to both of them. The go_to_school() action exists independently rather than living inside the definition of a specific student class.

What are the advantages of this method?

When writing procedural code, you only need to focus on what operations you want to execute on your data. As a result, your script aligns perfectly with your natural stream of consciousness. Think of it like writing an essay: you can simply pick up your pen and write down descriptions exactly as they come to mind. In contrast, if you were using OOP, you would first have to formally categorize whether your essay is descriptive or argumentative, as each type dictates a strict structural outline you are forced to follow from the start.

To give you an idea, here is a snippet of procedural code I wrote in R to calculate transport logistics costs for City B. It might look intimidating at a glance, but when building it, I simply scripted it block by block and then chained them together sequentially. The great thing about this approach is that no matter how complex your mathematical calculations get, as long as you follow a procedural flow, everything connects together intuitively.

What are the disadvantages of this method?

If you are developing a large-scale software system, since functions are not modularly encapsulated within specific objects, you can easily end up creating massive amounts of redundant code. For example, if you manually write the logic for "going to school" for a standard student, and then completely rewrite that exact logic block again for the class monitor, your program will still run correctly, but your code will be unoptimized and incredibly difficult to manage down the line.
